# 写真と多角形地面の実装判断

## Context

既存の庭は幅・奥行き、配置物、revisionを持つ`GardenDocument`で、3D表示とMySQL保存が動作する。従来は投影基準4点と庭輪郭を別々に入力していたため、最初の4クリックが輪郭に残らず、描画が終了したように見えた。要求は写真直後から「1→2→3→4→5…→1」の一連の操作で任意の輪郭を閉じることである。

## Decision

- 写真の元データはJPEG/PNGのdata URLとして`GardenDocument.photo`に入れ、既存のrevision付きPUTでMySQLの`gardens.photo_json`へ保存する。最大5MB、各辺6000px、総画素数2500万、輪郭64点まで。既存庭の`photo`は`null`として読み込む。保存形式は後方互換の`schemaVersion=1`の任意項目として扱う。
- 写真読み込み直後から3〜64点の単純多角形を描く。最初のクリックが庭の頂点1であり、4点目でも描画状態・点列を維持する。最後の頂点からポインターへの仮線を表示し、3点以上で始点1をクリックした時だけ検証済みの輪郭をGardenDocumentへ反映する。描画途中に閉じた面やグリッドは表示しない。
- `boundary`は元画像に対する0〜1の輪郭点列とする。交差、面積不足、画像外、重複や近すぎる点を拒否する。最後に始点を重複追加しない。
- `corners`はユーザー入力ではなく、輪郭の外接矩形から「下左→下右→上右→上左」の順で自動生成する内部の変換基準である。外接矩形を庭の幅・奥行きへ対応させ、既存の3×3変換とR3F地面メッシュ生成へ渡す。描画した多角形を四角形に置き換えない。
- 描画途中の頂点はZustandの一時状態として保持し、API DTOへ含めない。描画中は保存と3D切替を止め、取消時は以前の確定済み輪郭・変換を保持する。保存形式は変更せず、既存の写真・輪郭・投影基準は確定済みとしてそのまま読み込む。輪郭を確定し直す、または確定済み頂点をドラッグした時に外接矩形から変換基準を更新する。
- 写真モードは元画像上に地面・1mグリッドと、固定したThree.jsカメラによるGLB描画を重ねる。写真と3D庭は同じ配置データ・モデル読み込み・地面への配置処理を使う。3DモードだけOrbitControlsを使う。詳細は[写真への庭木表示](photo-tree-overlay.md)を参照する。
- 頂点番号は描画中だけ表示する。確定後は番号を隠し、橙色の点のドラッグと「庭の領域を書き直す」で修正できる。取消では以前の輪郭を保持し、配置物を自動削除しない。

## Alternatives

- 画像をブラウザーの一時URLやlocalStorageに置く方法は再読み込み後・別端末での復元に適さない。
- 専用ファイルストレージと参照IDを追加する方法は画像と庭のトランザクション整合、削除時の孤児ファイル処理が増える。ローカルMVPの5MB上限ではMySQL保存を選んだ。
- 写真の視点に3Dカメラを推定してGLBを直接合成する方法は高さ方向の拘束が足りず、今回の受け入れ条件を満たす精度を主張できない。
- 四隅の手動指定を必須の前段に残す方法は、一連の頂点クリックで輪郭を描く操作要件を満たさない。任意多角形の頂点だけでは各頂点の実測3D座標が不明なため、正確な遠近補正の対応点として扱わない。今回は外接矩形による平面への対応を採用する。

## Consequences

庭のJSON応答とPUTは画像分だけ大きくなる。写真の変更は庭の保存操作で確定し、競合時は既存のrevision検査を適用する。庭は名前だけで作成し、幅・奥行きは編集画面の「土台の辺の長さ」で変更する（[寸法編集](garden-dimensions.md)）。輪郭の変更後に既存配置物が地面外となっても、配置物の自動削除や位置補正は行わない。3Dグリッドは0.125m刻みで表示区間を近似して切り取る。

外接矩形による対応は写真の奥行き歪みを推定・補正しない。写真上の輪郭の形状を3D平面へ写す機能であり、地面の実測形状を写真だけから復元したとは主張しない。輪郭の外接矩形を変更すると、同じ配置物の3D座標に対応する写真上のモデルの根元位置は変わり得る。旧保存データは未編集で読み込み・保存する限り、従来の投影基準を保持する。DB列・API DTO・schemaVersionは変更しない。
