# 写真と多角形地面の実装判断

## Context

既存の庭は幅・奥行き、配置物、revisionを持つ`GardenDocument`で、3D表示とMySQL保存が動作する。写真上で地面を指定するため、画像座標とメートル座標の対応、および画像の永続化が必要だった。

## Decision

- 写真の元データはJPEG/PNGのdata URLとして`GardenDocument.photo`に入れ、既存のrevision付きPUTでMySQLの`gardens.photo_json`へ保存する。最大5MB、各辺6000px、総画素数2500万、輪郭64点まで。既存庭の`photo`は`null`として読み込む。保存形式は後方互換の`schemaVersion=1`の任意項目として扱う。
- 写真上の四隅は「手前左→手前右→奥右→奥左」で、元画像に対する0〜1の座標とする。四隅と庭の幅・奥行きから3×3のホモグラフィを求める。
- 地面の輪郭は四隅の内側にある独立した3〜64点の単純多角形とする。四隅は投影の基準、輪郭は実際の庭の地面範囲である。交差、面積ゼロ、四隅外へのはみ出しを拒否する。
- 投影基準の4点目で輪郭を自動生成しない。基準点の指定後は輪郭描画へ進み、最後の頂点からポインターへの仮線を表示する。3点以上で始点へ接続、または「輪郭を確定」で検証を通過した時だけ輪郭をGardenDocumentへ反映する。描画途中に閉じた面やグリッドは表示しない。
- 描画途中の頂点はZustandの一時状態として保持し、API DTOへ含めない。描画中は保存と3D切替を止め、取消時は以前の確定済み輪郭を保持する。保存形式は変更せず、既存の写真・輪郭は確定済みとして読み込む。
- 写真モードは元画像上に地面、1mグリッド、配置基準点のマーカーを投影する。写真モードでは3Dカメラを表示せず、画像座標は固定する。3Dモードでは写真を表示せず、同じ輪郭からR3Fの地面メッシュとグリッドを生成し、OrbitControlsを使う。
- 既存GLBは3Dモードで表示し、写真モードでは地面上の配置基準点をマーカーで示す。高さのある形状は一枚の写真と平面ホモグラフィだけでは正確に合成できない。

## Alternatives

- 画像をブラウザーの一時URLやlocalStorageに置く方法は再読み込み後・別端末での復元に適さない。
- 専用ファイルストレージと参照IDを追加する方法は画像と庭のトランザクション整合、削除時の孤児ファイル処理が増える。ローカルMVPの5MB上限ではMySQL保存を選んだ。
- 写真の視点に3Dカメラを推定してGLBを直接合成する方法は高さ方向の拘束が足りず、今回の受け入れ条件を満たす精度を主張できない。

## Consequences

庭のJSON応答とPUTは画像分だけ大きくなる。写真の変更は庭の保存操作で確定し、競合時は既存のrevision検査を適用する。幅・奥行きは庭の作成時に入力し、既存の寸法不変ルールを維持する。輪郭の変更後に既存配置物が地面外となった場合は写真モードで赤いマーカーとして示すが、配置物の自動削除や位置補正は行わない。3Dグリッドは0.125m刻みで表示区間を近似して切り取る。
