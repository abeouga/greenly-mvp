# 写真上への庭木表示の検証

実行日: 2026-10-02（JST）

## 要件と証拠

| 要件 | 確認内容 |
| --- | --- |
| 3D庭に置いた木を写真にも表示 | Nで3D庭から木を配置し、写真画面へ切り替えてGLBの読み込みと表示を確認。配置の表示ON/OFFで画像が変わることを確認 |
| 写真画面から木を設置 | Nで写真の領域内に2本目をクリック配置し、実APIのX/Z座標が写真座標に対応することを検査。領域外クリックでは追加されない |
| 同じ木を両画面で保持 | 保存・再読み込み後に写真と3D庭の双方で2本を表示。位置・回転・倍率・IDをGardenDocumentで共有 |
| 写真のカメラを固定 | 写真画面のドラッグ前後で描画画像が同一であり、配置物が増えないことを確認 |
| 確定後に頂点番号を隠す | Nで描画中の番号6個、確定・再読み込み後の番号0個、書き直し中の番号復帰を検査 |
| 領域を書き直す | Nで開始・取消・4点への再確定・保存復元を確認。配置物のIDと変換を保持 |

Chromium、実FastAPI、実Vite、専用MySQL DBを使用した。正常系APIはモックしていない。写真は800×600pxの合成PNGであり、実利用者の写真ではない。

## 実行結果

- npm run precheck: 型チェック、lint、Python compile通過。
- npm run build:web: 最終CSS修正後も通過。既存の500kB超バンドル警告あり。
- A（既存3D配置・変形・保存復元）: 9.1秒で通過。
- 最終の対象E2E I・N: 2件通過、18.5秒。Iは5.1秒、Nは8.4秒。
- 変更したソース・ドキュメントのgit diff --check: 通過。
- Chromeの確認用庭で読み込み済み2/2、保存済み、頂点番号なし、領域書き直しボタン、写真上の2本のGLB表示を直接確認した。

全E2Eの再実行はしていない。変更に関係するフローだけを実行した。

## 検出した失敗と修正

初回は実行途中でAPI・Viteのプロセスが終了し、通信が拒否された。終了原因は未確定であり、合格扱いにしなかった。記録は[photo-tree-server-stop](photo-tree-server-stop/)に保持した。

次の実行で画面サイズ変更後の写真クリック位置と保存座標の不一致を検出した。SVGの拡縮とR3FのキャンバスCSSサイズが二重に適用されていたため、写真内キャンバスのCSS幅・高さを親の100%へ固定した。座標期待値は変更せず再実行し、通過した。失敗trace・スクリーンショット・レポートは[photo-tree-coordinate-mismatch](photo-tree-coordinate-mismatch/)に保持した。

## 2026-10-02 木の傾きの修正

高さが増えると横位置も変化する投影を修正し、木の高さ方向を画面の垂直方向へ合わせた。根元の地面座標は維持する。同じカメラの逆投影を使ってクリックのレイも更新した。

- ユーザーのChromeで、実写の庭写真と確認用の合成画像の両方を目視した。2本の幹が垂直で、選択枠の縦辺も傾いていないことを確認した。
- 確認用の庭はChromeで再読み込み後も2本のGLBが表示され、保存済み・読み込み済み2/2だった。[Chromeの確認画像](photo-trees-upright-chrome.jpg)を保存した。実利用者の写真は成果物へ複製していない。
- `npm run precheck`、`npm run build:web`通過。ビルドには従来の500kB超バンドル警告がある。
- 対象E2E Nを実API・MySQLで実行し、1件通過（テスト8.6秒、全体13.8秒）。写真上のクリック配置座標、モデル選択、固定視点、保存・再読み込み、領域再設定を確認した。画像とAPI JSONは上記の成果物を更新した。
- 初回Nは、APIがID順で返す配列をテストが配置順と誤認して失敗した。両方の配置座標は正しかった。配置時のIDで照合するようテストを修正し、座標の期待値は維持した。失敗時のtraceとレポートは[photo-tree-object-order](photo-tree-object-order/)へ保存した。

垂直な表示の証拠はChrome画面の目視確認である。E2Eの成功だけで傾きの解消を判定していない。撮影カメラの正確な再現や写実的な合成は引き続き保証しない。
